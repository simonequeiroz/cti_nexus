# CTI Nexus

Trabalho **individual** de Simone Queiroz (SENAI, Projeto Integrador II, 2026), baseado no desafio "Sistema CTI Insights" da empresa Provedor CTI. O CTI Insights é o projeto da equipe (com sprints e divisão back-end/Python/banco/nuvem); o CTI Nexus é a versão individual para avaliação individual. Plataforma que recebe planilhas comerciais bagunçadas (Excel), valida e padroniza os dados e mostra relatório de qualidade, dashboard e insights.

Referências da atividade: plano de ensino 5.01-FR-97 v.4 (PI-2 2026), com stack Vue 3 + Tailwind + Chart.js + Vue Router + axios, Spring Boot, Python/Pandas, Neon PostgreSQL, Vercel/Render; e o dicionário de dados da planilha da aula (aba `upload_clientes`: codigo_cliente, nome_cliente, consultor, segmento, nivel_cliente, faturamento_anual, servicos_contratados, data_contratacao, cidade e uf opcionais). A coluna opcional `email` foi acrescentada para a atividade "Pinia - Validação de Planilha" (pede e-mails inválidos).

## Estrutura

- `frontend-vue/`: Vue 3 + Vite + Tailwind CSS v4 + Pinia + `xlsx` (SheetJS) para ler planilhas.
- `backend-java/`: Spring Boot 4.1 (Java 21), pacote `br.com.ctinexus`, segue a Aula 10 de back-end (JWT). Feito: cadastro (pedido de acesso, entra PENDENTE), login com BCrypt + JWT, `/api/auth/me`, tela Usuários (`/api/admin/usuarios`: GET, POST, PUT `/{id}`, PATCH `/{id}/status` com `{situacao, papel}`, DELETE `/{id}` recusa pedido; exige a permissão `gerenciar_usuarios`). Erros em `{status, mensagem, campos}`; `RegraDeNegocioException` com campo faz o front mostrar o erro embaixo do campo certo. Pastas em inglês (model, repository, dto, service, security, config, controller), classes em português e comentadas como no front. As permissões ficam no enum `Papel` (mesmos códigos de `constants/permissoes.js`) e viram authorities no `JwtFiltroAutenticacao`. Senhas e chave vêm de variáveis de ambiente, lidas também do `backend-java/.env` (só local, ignorado pelo Git; modelo em `.env.example`; banco no Neon, região sa-east-1); `DadosIniciais` cria o 1º administrador e, com `DEMO_USUARIOS=true` (padrão), `analista@` e `gestor@ctinexus.com` (senha `123456`). Testes: `mvn test` (H2 em memória). Detalhes no `backend-java/README.md`. Já ligado ao front (login, pedido de acesso e tela Usuários).
- `analytics-python/`, `database/`: por enquanto só arquivos vazios (Pandas/Matplotlib e PostgreSQL planejados).
- `landing.html`: landing page institucional independente do app Vue.

## Como rodar

Instalar **dentro** da pasta do front: `cd frontend-vue` e `npm install`. Depois, na raiz ou em `frontend-vue`, `npm run dev` (http://localhost:5173). Depois de todo `git pull` que alterar `frontend-vue/package.json`, rodar `npm install` de novo (sem isso aparece erro de import, ex.: "failed to resolve import pinia").

Não usar `npm install --prefix frontend-vue` na raiz: o npm instala a própria raiz como dependência (`"projeto-cti-nexus": "file:.."` no `package.json` e um atalho em `node_modules`). Se aparecer isso no `git status`, desfazer.

Se uma mudança não aparecer no navegador (ex.: página nova cai na landing), o Vite pode não ter percebido a alteração no Windows: parar com Ctrl+C e rodar `npm run dev` de novo, com um servidor só.

## Frontend: convenções

- **Textos da tela em linguagem do consultor da CTI (usuário final, não técnico).** Nada de ETL, upload, dashboard, insights, status, registros, padronização, CSV, sessão/Pinia. Exceção pedida pela Simone: os nomes das etapas (sidebar, menu do celular e "Passo N de 4 — …") são Upload, Validação, Relatório, Dashboard. Vocabulário usado no resto: Enviar planilha / Conferir planilha, Conferir de novo, Painel da carteira, "prontas para a análise", aprovadas / com erro, ajustes automáticos, Situação, Código repetido, "Passo N de 4". Termos estatísticos pedidos no plano (média, mediana, desvio padrão) ficam, mas com explicação simples. Nomes no código e rotas (`PaginaUpload`, `#upload`...) continuam técnicos.

- **Tudo em português**: nomes de arquivos, componentes, variáveis, funções e comentários. Componentes em PascalCase português (`BotaoBase`, `PaginaUpload`, `TabelaDetalhesErros`). Só ficam em inglês os nomes padrão do ecossistema: `App.vue`, `main.js`, `style.css` e as pastas `components/`, `views/`, `router/`, `services/`, `stores/`, `composables/`, `utils/`, `constants/`.
- Pastas de componentes por tela: `components/inicio/`, `login/`, `upload/`, `relatorio/`, `usuarios/`, `layout/`, e `ui/` para peças reutilizáveis.
- Telas internas usam `LayoutSistema`: no desktop, a sidebar "Trilha do dado" (`TrilhaDados.vue` + `EtapaTrilha.vue`) mostra Upload → Validação → Relatório → Dashboard com o status real da `uploadStore`. Ela é recolhível (240px ↔ 80px); o estado fica em `composables/useMenuLateral.js`, salvo no localStorage. No celular aparece o `CabecalhoSistema`.
- Páginas (telas) em `src/views/`, como pede o plano de ensino, mantendo os nomes em português (`PaginaInicial`, `PaginaLogin`, `PaginaCadastro`, `PaginaUpload`, `PaginaValidacao`, `PaginaRelatorio`, `PaginaDashboard`, `PaginaUsuarios`).
- Cada tela tem uma função, para não repetir informação: **Upload** = enviar e ver o resultado rápido (`ResultadoValidacao`: resumo por tipo, nº de padronizações, botões "Corrigir N linhas" / "Ver relatório"), dados válidos e histórico (sem faixa de indicadores; o histórico não lista erros, só o motivo de leitura que falhou, e o registro da planilha aberta é atualizado ao `revalidar`; trilha de auditoria: cada envio guarda `enviadoPor` { id, nome } do usuário logado e a hora, mostrados no histórico e no cabeçalho do Relatório — no banco vira `importacao.enviado_por`, com o id, nunca o nome); **Validação** = único lugar para ver e corrigir erros linha a linha + padronizações + log "quem alterou o quê" (`RegistroAlteracoes`) + liberação para o painel (`CartaoLiberacao`); **Relatório** = documento para ler/exportar/imprimir (aviso de status já com a qualidade; detalhes de erros e padronizações recolhidos na tela e sempre completos na impressão, via `print:flex` e `beforeprint`); **Dashboard** = análise dos clientes **liberados** (`dadosLiberados`, não `dadosValidos`), com os 3 insights mais importantes no topo (`DestaquesInsights`) e o resto na `ListaInsights`, sem repetir.

- Liberação para o painel (o "L" do ETL, permissão `aprovar_carga`): `liberarParaPainel()` copia `dadosValidos` para `dadosLiberados` e guarda `liberacao` { por, em, quantidade }. Correções depois disso marcam `mudouDesdeLiberacao` e o painel continua com a versão liberada até liberar de novo. Conferir a planilha de novo (`processarArquivo`) zera liberação e alterações. No banco: `importacao.aprovado_por/aprovado_em`.
- Log de alterações: `corrigirCampo` registra em `alteracoes` (usuário, linha, código, campo, valor antigo e novo, data); edições do mesmo campo na mesma rodada (antes de `revalidar`) viram um registro só. Aparece na Validação e nos detalhes do Relatório. No banco: tabela de alterações ligada à importação.
- Tempo da conferência: `duracaoMs`, mostrado no resultado do Upload e no histórico (`formatarDuracao`).
- Rotas com Vue Router em `src/router/index.js`, modo hash (`createWebHashHistory`: endereços `#/login`, `#/cadastro`, `#/upload`, `#/validacao`, `#/relatorio`, `#/dashboard`, `#/usuarios`, `#/trocar-senha`). Escolhido para trocar de tela sem recarregar (a planilha carregada fica na memória) e para a Vercel não precisar de rewrite. Cada rota tem `meta.permissao` (ou `meta.publica` no login e cadastro); o `beforeEach` manda para `/login` sem login, para `auth.telaDeEntrada` sem permissão ou se já logado em tela pública; endereço desconhecido volta para `/`. `App.vue` só tem `<RouterView />`. Nos componentes: `useRoute().path` para a tela atual, `useRouter().push()` para navegar, e links como `href="#/upload"` (listas de menu guardam `'/upload'` e o `href` põe o `#` na frente). `PERMISSAO_DA_TELA` e `telaInicial` usam `'/upload'`.
- Comunicação com o back-end: `src/services/api.js` (axios com `baseURL` de `VITE_API_URL` do `frontend-vue/.env`, modelo em `.env.example`; interceptor manda `Authorization: Bearer` com o token do `sessionStorage`). `VITE_API_URL=http://localhost:8080/api` (todas as rotas do Spring começam com `/api`); sem `.env` (ele não vai para o GitHub), o `api.js` usa esse mesmo endereço (`ENDERECO_API`). Uma função por rota em `services/autenticacaoService.js` (`entrar`, `pedirAcesso`, `buscarUsuarioLogado`) e `services/usuariosService.js` (`listarUsuarios`, `cadastrarUsuario`, `editarUsuario`, `alterarSituacao`, `recusarPedido`); as stores chamam os services, nunca o axios direto (pedido da professora: deixar visível que o front está ligado ao back). O `api.js` concentra a comunicação: `timeout` de 30 s, interceptor de ida (token) e de volta (401 com alguém logado: `logout` e volta ao login). O `main.js` só chama `auth.conferirSessao()` (`GET /auth/me`) ao abrir. A API manda papel/situação em maiúsculas; `utils/usuarioApi.js` converte para o formato das telas (`papel` minúsculo, `ativo`, `pendente`) e transforma erros da API em mensagem ou erros por campo (`geral` quando não é de um campo).
- Validação (`#/validacao`): linhas com erro editáveis (`components/validacao/LinhaInvalida.vue`). As ações `corrigirCampo`, `revalidar` e `baixarPlanilhaCorrigida` da `uploadStore` alteram `dadosBrutos` e rodam `validarDados()` de novo; as correções não persistem ao recarregar a página.
- Dashboard (`components/dashboard/`): Chart.js via `GraficoBase.vue` (tabela sr-only). Cores em `constants/cores.js`: cada segmento tem uma cor fixa em todos os gráficos (paleta validada para daltonismo em todos os pares; sem laranja/verde-limão, que significam erro/válido), nível A/B/C numa escala de azul (A escuro, C claro) e medidas únicas (contratações, histograma, serviços) no azul da marca. Cor nunca sozinha: sempre com nome no eixo, legenda ou tabela. Tipos de gráfico seguem o plano de ensino (barras, linha, dispersão, histograma); todos em Chart.js, sem boxplot no front (a Simone decidiu tirar; "Estatísticas do faturamento" usa barras com a média por grupo + tabela com média, mediana e desvio padrão). O plano de ensino **exige boxplot** (faturamento por segmento) entre os 4 gráficos de Ciência de Dados, "gerados em Python": ele precisa existir no `analytics-python/graficos.py` (Matplotlib); o nível A/B/C é uma rosca (cobre o "pizza" do plano), com total no miolo e legenda com %. Gráficos recebem `clientes` (válidos e filtrados) por prop. Estatística em `utils/estatistica.js`; meses, histograma e insights (formato da classe Insight: titulo, descricao, tipo, prioridade) em `utils/dadosDashboard.js`.
- Stores Pinia no estilo setup, com seções `// ===== STATE =====`, `GETTERS`, `ACTIONS`: `autenticacaoStore.js` (`useAutenticacaoStore`, id `'auth'`) e `uploadStore.js` (estado do upload; só orquestra leitura e validação).
- Regras fora da store, em funções puras: `utils/leituraPlanilha.js` (aba `upload_clientes` ou a primeira, CSV UTF-8/ANSI, erros `ExcelInvalidoError` e `ColunaObrigatoriaError`, que imitam as exceções previstas para o Spring Boot), `utils/validacao.js` (`validarLinhas`: padronização + regras do dicionário; e-mail opcional conferido por `emailValido`; cada ajuste automático leva um `motivo` de `MOTIVOS_DE_AJUSTE` — Espaços extras, Maiúsculas e minúsculas, Escrita padronizada, Formato do valor —, contado no getter `padronizacoesPorMotivo`; código repetido diz em que linha apareceu primeiro) e `utils/normalizacao.js`. Listas fixas (segmentos, níveis, colunas obrigatórias) em `constants/validacao.js`.
- Limites do upload (`constants/validacao.js`): .xlsx/.xls/.csv, até 5 MB (`verificarArquivo`, antes de ler) e até 20.000 linhas (conferido pela área da aba, antes de converter). 20 mil linhas levam ~1,6 s para ler e validar. Quando existir o back-end, usar o mesmo limite no Spring: `spring.servlet.multipart.max-file-size=5MB` (o padrão dele é 1 MB).
- Testes com Vitest: `npm test` na pasta `frontend-vue` (arquivos `*.test.js` ao lado do código em `utils/`, `constants/` e `stores/`; `uploadStore.test.js` roda o fluxo completo com a planilha de teste). Testes que fazem login trocam a API por `services/apiFalsa.js` (`vi.mock('../services/api', () => import('../services/apiFalsa'))`), que imita o Spring; chamar `api.reiniciar()` no `beforeEach`.
- Login pela API (`POST /auth/login`): token e usuário no `sessionStorage` (chaves `token` e `cti-nexus-usuario`). Usuários de demonstração criados pelo back-end, um por papel, todos com senha `123456` (`admin@`, `analista@`, `gestor@ctinexus.com`; lista `USUARIOS_DEMO` na `autenticacaoStore`). Na tela de login, o acesso de demonstração fica recolhido ("Usar acesso de demonstração") e some com `VITE_MOSTRAR_DEMO=false`; dentro dele, uma linha de 3 botões pequenos com o papel (Administrador, Analista de Operações, Gestor), sem nome nem senha na tela; o clique chama `auth.loginDemonstracao(email)`, que faz o login normal com a senha de demonstração (se o administrador mudar o e-mail ou a senha, ou desativar, o botão mostra o erro do login); "Esqueci minha senha" usa senha temporária com troca obrigatória (sem e-mail; ver abaixo) e "Não tem acesso?" leva ao pedido de acesso (`#/cadastro`). Os usuários ficam no banco; a `usuariosStore` (`useUsuariosStore`) só guarda a lista que veio da API (`carregar()`, chamado pelo `LayoutSistema` quando quem entrou é administrador, o que também alimenta o número de pedidos na trilha). As ações (`pedirAcesso`, `cadastrar`, `editar`, `aprovarPedido`, `alternarAtivo`, `recusarPedido`) são assíncronas: rodam a validação local e depois chamam a API.

- Esqueci minha senha ("jeito 3", escolhido pela Simone): no login, o quadro "Esqueci minha senha" chama `POST /auth/esqueci-senha` (resposta sempre igual, exista o e-mail ou não), que marca `usuario.pediu_nova_senha_em`. O administrador vê o quadro `PedidosNovaSenha` na tela Usuários (o número ao lado de "Usuários" soma pedidos de acesso + de nova senha: `quantidadeAguardando`) e define uma senha temporária (`PATCH /admin/usuarios/{id}/senha`). Senha temporária = `usuario.deve_trocar_senha`: o login funciona, mas sem permissão nenhuma (no back, `JwtFiltroAutenticacao` não dá authorities; no front, `auth.pode()` responde false) e o router manda para `#/trocar-senha` (`PaginaTrocarSenha` + `FormularioTrocaSenha`: senha temporária, nova, confirmação; `POST /auth/trocar-senha`). Depois de salvar, faz `logout` e volta ao login (`#/login?senha=alterada&email=...`: aviso "Senha alterada com sucesso" e e-mail preenchido), para a pessoa entrar com a senha nova (pedido da Simone). Também vale como temporária a senha que o administrador digita ao cadastrar alguém ou ao editar a senha de outra pessoa (a própria não). Login com a senha certa limpa o pedido. Etiqueta "Senha temporária" na `TabelaUsuarios`. Regras do formulário em `validarTrocaSenha` e `validarSenhaTemporaria` (`utils/validacaoUsuario.js`).

## Níveis de acesso (RBAC) — regra do sistema

O sistema lida com dados sensíveis (clientes, faturamento), então o acesso é separado por papel:

- **Administrador / Engenheiro de Dados**: acesso total. Configura conexões, cria regras de transformação (regras de negócio para correções) e limpa o histórico.
- **Analista de Operações / Suporte CTI**: importa as planilhas, vê os erros de validação, faz correções manuais na tela e aprova a carga dos dados.
- **Gestor / Diretor** (consumidor de insights): só visualiza. Não altera dados; vê painéis, relatórios e indicadores.

Como está no front: papéis e permissões em `constants/permissoes.js` (testado em `permissoes.test.js`). Telas e botões conferem a **permissão** (`auth.pode('corrigir_dados')`), nunca o nome do papel. O `router.beforeEach` bloqueia a tela sem permissão e manda para `auth.telaDeEntrada` (gestor começa no `/dashboard`). Etapas da trilha sem permissão ficam sem link ("sem acesso"). Permissões `aprovar_carga`, `configurar_conexoes` e `gerenciar_regras` já existem, mas ainda não têm tela.

Cadastro de usuário (exigência da professora): tela `#/usuarios` (`PaginaUsuarios`), só para quem tem `gerenciar_usuarios` (administrador), escolhendo o papel. Ninguém escolhe o próprio papel, então não há "criar conta" público: no login, "Não tem acesso? Pedir acesso" leva a `#/cadastro` (`PaginaCadastro` + `FormularioPedidoAcesso`: nome, e-mail, cargo opcional, senha). `pedirAcesso` grava o usuário com `pendente: true`, `papel: null`, `ativo: false` (login recusado com "pedido ainda não aprovado"); o administrador vê o número de pedidos ao lado de "Usuários" na trilha e no menu do celular (some quando não há pedidos) e o quadro `PedidosAcesso` na tela Usuários (só aparece com pedidos), escolhe o papel e aprova (`aprovarPedido`) ou recusa (`recusarPedido`, remove o pedido, pois nunca teve acesso). A lista de usuários (`cadastrados`, `usuariosOrdenados`) não inclui pedidos. Regras em `validarPedidoAcesso` (mesmas do cadastro, sem papel). No banco (feito): tabela `usuario` com `papel` (texto, nulo no pedido) e `situacao` (PENDENTE/ATIVO/DESATIVADO). Regras do formulário em `utils/validacaoUsuario.js` (testado). Usuário é desativado, nunca apagado. Proteções: ninguém desativa a si mesmo nem muda o próprio papel, e o sistema nunca fica sem administrador ativo (`ultimoAdministrador`).

No banco: por enquanto o papel é um enum (`Papel.java`) com a lista de permissões, gravado como texto em `usuario.papel`; as tabelas `papel`, `permissao` e `papel_permissao` ficam como evolução possível. Mesmos códigos de permissão do front. O Spring Boot confere a permissão de novo em cada rota da API; esconder botão no front não protege o dado.
- Planilhas oferecidas na tela de upload, geradas por `npm run planilhas` (`scripts/gerarPlanilhas.js`, usa `constants/validacao.js`): `public/modelo-clientes.xlsx` (aba `upload_clientes` com 2 linhas corretas + aba `dicionario`) e `public/teste-clientes.xlsx` (15 linhas despadronizadas de propósito: 5 válidas e 10 com erro). Depois de mudar regras em `constants/validacao.js`, rodar `npm run planilhas` de novo; `src/utils/planilhasPublicas.test.js` confere os dois arquivos.
